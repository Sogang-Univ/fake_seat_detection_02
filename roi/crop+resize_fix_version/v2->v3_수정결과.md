맞아. **지금은 전체 `crop_and_resize`를 통째로 파이프라인화한 게 아니라, 그 안의 일부 구간만 DATAFLOW로 겹친 상태야.**

현재 구조를 정확히 보면:

```text
한 output row 처리

① 필요한 source row LOAD
        │
        │  아직 순차 실행
        ▼
② RESIZE
        │
        │
        ├── DATAFLOW 적용 ✅
        │
③ DDR WRITE
        │
        ▼
다음 output row
```

즉 우리가 이번에 만든 것은 **② Resize ↔ ③ Write 사이의 파이프라인**이야.

합성 결과에서도 정확히 그렇게 나와:

```text
load_row
Latency = 235 cycles
    ↓
resize_row_dataflow
Latency = 652 cycles
    ├─ resize_pixel_loop II=1
    └─ write_output II=1
```

`resize_row_dataflow*`에 `dataflow`라고 표시된 반면, 최상위:

```text
out_row_loop
Pipelined = no
```

는 그대로지. 이게 **전체 row 처리 파이프라인은 아직 아니라는 증거**야.

### 현재 파이프라인 수준을 나누면

```text
레벨 1: Pixel pipeline
────────────────────────
resize_pixel_loop
II = 1
✅ 이미 되어 있음


레벨 2: Resize ↔ Write
────────────────────────
Resize ─────────────
       Write ──────
✅ 이번에 추가


레벨 3: Load ↔ Resize ↔ Write
────────────────────────────
Load N+1 ─────
Resize N  ───────────
Write N       ──────

❌ 아직 안 함


레벨 4: Output row끼리 중첩
────────────────────────────
Row N
Row N+1
Row N+2 ...

❌ 아직 안 함
```

우리가 처음부터 전체 DATAFLOW를 하지 않은 이유도 있어. **bilinear resize는 앞뒤 source row를 재사용하기 때문**이야.

예를 들어 480→640 확대라서 대략:

```text
output row 0 → source row 0,1
output row 1 → source row 0,1
output row 2 → source row 1,2
output row 3 → source row 2,3
...
```

처럼 움직여.

그래서 현재 코드에는:

```cpp
line0
line1
phase
cached_row
```

가 있고, 필요할 때만 DDR에서 새로운 source row를 읽어. 이 상태에서 단순히 최상위에 `#pragma HLS DATAFLOW`를 걸면 **load가 쓰는 line buffer와 resize가 읽는 line buffer가 충돌**할 수 있어.

그래서 전체 파이프라인으로 가려면 다음 단계에서는 **ping-pong buffer** 구조가 필요해.

```text
현재
─────
LOAD → line0/line1
          ↓
       RESIZE
          ↓
        WRITE


다음 단계
─────────
LOAD N+1 → Buffer Set B
              │
RESIZE N  ← Buffer Set A
              │
WRITE N-1

다음 iteration에서는

LOAD N+2 → Buffer Set A
RESIZE N+1 ← Buffer Set B
WRITE N
```

즉 A/B 두 세트를 번갈아 사용하는 거야.

다만 한 가지 중요한 점은, **지금 부분 DATAFLOW만으로도 실제 효과가 상당히 분명했다는 것**이야.

```text
128-bit 최적화
827,051 cycles

        ↓ Resize/Write만 DATAFLOW

현재
723,303 cycles
```

약 **12.5% 추가 감소**했고, BRAM도 FIFO를 조정해서 오히려:

```text
20 → 16 BRAM
```

으로 낮췄어.

그래서 현재 단계는 이렇게 보면 정확해:

> **1차 DATAFLOW 최적화 완료: Resize와 DDR Write를 overlap**
>
> **2차 DATAFLOW 최적화 미완료: DDR Load와 Resize까지 overlap**

우선 지금 만든 1차 DATAFLOW 버전을 실제 KV260에서 측정해서 `6.57 ms → ? ms`인지 확인하는 게 좋아. 그 개선 폭을 본 다음, 가치가 있으면 **2차로 `Load ↔ Resize ↔ Write` 전체 stage pipeline + ping-pong line buffer**까지 진행하면 돼.
