부분적으로는 해결됐고, **네가 말한 “단계 간 파이프라인” 문제는 아직 해결하지 않았어.** 이 둘을 구분해야 해.

지금 내가 해준 수정은 **각 루프 내부의 처리 효율을 개선한 것**이야. 예를 들어 `out_col_loop`는 이미 `II=1`이라서 매 클럭마다 새 픽셀을 받아 처리할 수 있었고, 이번에 `write_output`도 `II=3 → II=1`로 개선했어. `load_row()`의 불필요한 `tmp → line buffer` 복사도 없앴고. 그래서 전체 합성 latency가 약 `12.9 ms` 수준에서 `8.27 ms` 예상으로 줄어든 거야.

하지만 내가 전에 말했던 더 큰 의미의 파이프라인, 즉 **load / resize / write를 서로 겹쳐 실행하는 구조**는 아직 안 들어갔어.

현재 새 코드도 기본적으로 한 row에 대해 이렇게 움직여:

```text
① 필요한 입력 row load
████

② 640픽셀 resize
    █████████████

③ 결과 row DDR write
                 ███

④ 다음 row 처리
                    ████...
```

즉 `load_row()`가 끝난 다음 resize하고, resize가 끝난 다음 write하고, 그게 끝나야 다음 row로 넘어가.

그래서 `csynth.rpt`에서도 top-level `out_row_loop`가:

```text
Pipelined = no
```

로 나왔지.

반면 내부 루프는:

```text
load_row_loop   II = 1
out_col_loop    II = 1
write_output    II = 1
```

이야.

이 차이가 핵심이야.

### 지금 상태를 정확하게 표현하면

```text
                 현재 구조

Frame
  │
  ├─ Row 0
  │    ├─ LOAD      ← 내부 II=1
  │    ├─ RESIZE    ← 내부 II=1
  │    └─ WRITE     ← 내부 II=1
  │
  ├─ Row 1
  │    ├─ LOAD
  │    ├─ RESIZE
  │    └─ WRITE
  │
  └─ ...
```

각 작업 자체는 빠르게 파이프라인되어 있지만 **세 작업이 시간적으로 겹치지는 않는 상태**야.

우리가 최종적으로 노려볼 구조는 이런 거야.

```text
시간 ───────────────────────────────→

LOAD     Row0   Row1   Row2   Row3
          ███    ███    ███    ███

RESIZE          Row0   Row1   Row2   Row3
                 █████  █████  █████

WRITE                   Row0   Row1   Row2
                         ███    ███
```

즉 Row 1을 DDR에서 읽는 동안 Row 0은 resize하고, 이전 Row는 DDR에 쓰는 식이야.

이게 HLS의 `DATAFLOW` + ping-pong buffer 같은 구조로 구현하는 **단계 간 파이프라이닝**이야.

그리고 현재 report에서 한 row의 `Iteration Latency`가:

```text
1292 cycles
```

인 것도 이걸 보여줘. 주요 작업이 대략:

```text
load_row       ≈ 235 cycles  (필요한 경우)
resize         ≈ 649 cycles
write_output   ≈ 163 cycles
+ 제어/조건 등
```

처럼 **더해져서** 한 row 시간이 결정되고 있어. 서로 겹쳐지면 합이 아니라 가장 느린 stage의 throughput에 가까워질 가능성이 생겨.

그래서 질문에 대한 답을 딱 나누면:

| 항목                              | 이번 코드에서 해결?           |
| ------------------------------- | --------------------- |
| Bilinear pixel pipeline         | ✅ 이미 II=1             |
| Input load loop pipeline        | ✅ II=1                |
| Output write loop pipeline      | ✅ **II=3 → II=1로 개선** |
| 불필요한 row copy                   | ✅ 제거                  |
| 128-bit 출력 인터페이스                | ✅ 개선                  |
| **Load ↔ Resize ↔ Write 동시 실행** | ❌ 아직                  |
| **Top-level DATAFLOW**          | ❌ 아직                  |
| **Ping-pong buffering**         | ❌ 아직                  |

그러니까 이번 수정은 **“잘못된 파이프라인을 완전히 해결한 최종판”이라기보다, DATAFLOW를 하기 전에 각 stage를 먼저 정상화한 1차 최적화**라고 보면 가장 정확해.

그리고 이 순서가 나쁜 게 아니야. 바로 DATAFLOW를 넣었다면 `write_output II=3` 같은 병목이 숨어 있는 상태에서 구조만 복잡해졌을 거야. 지금은 세 stage 중 resize와 write가 모두 II=1이 됐고, 불필요한 복사도 제거됐기 때문에 **다음 단계에서 stage 간 overlap을 시도하기 훨씬 좋은 상태**가 됐어.

따라서 지금 만드는 xclbin으로 먼저 `8.27 ms` 예상이 실제 보드에서 어느 정도 나오는지 확인한 뒤, **2차 최적화에서 DATAFLOW/ping-pong 구조를 적용하는 게 맞아.** 그 단계까지 가야 “FPGA의 파이프라인 이점을 제대로 활용했다”고 말할 수 있어.
