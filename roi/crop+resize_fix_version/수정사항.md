이 결과면 원인이 거의 확정됐습니다.

지금 HLS 경로 약 20.5 ms의 구성은:

Packing: 0.70 ms
H2D sync: 0.03 ms
HLS kernel: 12.87 ms
D2H sync: 0.006 ms
Unpacking: 6.52 ms
Wrapper overhead: 0.39 ms

즉 메모리 전송이 병목이 아닙니다. H2D/D2H는 거의 무시 가능한 수준입니다.

핵심 병목은 두 군데입니다.

HLS kernel 자체가 12.87 ms
출력 unpacking이 6.52 ms

그래서 지금 구조에서 “PL인데 왜 CPU OpenCV 5 ms보다 느리냐”의 답은 꽤 명확합니다.

현재 HLS 구현 자체가 약 12.9 ms로 OpenCV crop+resize 약 5.2 ms보다 느리고, 여기에 32-bit RGBx → BGR 변환 비용 약 6.5 ms까지 추가되어 전체 HLS 경로가 약 20.5 ms가 된다.

즉 지금은 인터페이스보다 HLS 설계 자체를 개선해야 하는 상황입니다.

그리고 흥미로운 점은 예전에 standalone HLS가 약 12.76 ms였는데 이번 순수 kernel 측정이 12.872 ms입니다. 거의 동일합니다. 그래서 측정도 일관적입니다.

지금 무엇을 바꿔야 하냐

우선순위는 이렇습니다.

첫째, HLS kernel 12.87 ms를 줄이는 게 최우선입니다. 현재 100 MHz 기준으로 대략 1.287 million cycles/frame입니다. 출력이 640×640 = 409,600 pixels이므로 평균적으로 출력 픽셀 하나당 약 3.14 cycles 정도입니다.

이건 이상적인 fully pipelined 구조라면 더 줄일 여지가 있습니다. 목표는 가능하면 출력 1 pixel/cycle에 가까워지는 것입니다.

둘째, unpacking 6.52 ms는 하드웨어 밖 PS 코드 문제입니다. 이건 나중에 꽤 쉽게 줄일 수 있습니다. 예를 들어 HLS가 처음부터 DPU가 원하는 byte layout으로 출력하게 만들거나, RGBx를 BGR로 다시 풀지 않고 바로 quantization까지 결합하면 됩니다.
