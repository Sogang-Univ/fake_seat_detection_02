이번 결과는 **PL 전처리 + DPU 전체 통합이 정상적으로 성공한 상태**야. 데이터 형식도 맞고, 850프레임 동안 안정적으로 돌아갔어.

최종값을 보면:

| 단계                      |         평균 시간 |
| ----------------------- | ------------: |
| Capture                 |     23.102 ms |
| PL 전처리 전체               |  **7.783 ms** |
| └ Packing               |      0.677 ms |
| └ HLS crop+resize+quant |  **5.954 ms** |
| └ Memcpy                |      0.620 ms |
| DPU                     | **17.496 ms** |
| Decode + NMS            |  **9.185 ms** |
| 상태 로직                   |      0.053 ms |
| **Processing 합계**       | **34.516 ms** |
| Processing 성능           | **28.97 FPS** |
| 실제 Wall FPS             | **13.70 FPS** |

즉 지금 FPGA/DPU 연산 자체는 거의 **29 FPS 처리 능력**이 있어. 문제는 실제 카메라 루프가 현재 완전히 순차적이라는 거야.

```text
현재 구조

cap.read()          23.1 ms
     ↓
PL preprocess        7.8 ms
     ↓
DPU                  17.5 ms
     ↓
Decode                9.2 ms
     ↓
화면 출력 등
```

카메라를 기다리는 동안 FPGA와 DPU가 놀고 있고, FPGA/DPU가 처리하는 동안에는 다음 카메라 프레임을 미리 받아오지 않아.

그래서 `processing FPS = 28.97`인데 실제 `wall FPS = 13.70`까지 떨어지는 거야.

### 지금 전처리 자체는 성공으로 확정해도 돼

특히 중요한 결과는:

```text
HLS       5.954 ms
Memcpy    0.620 ms
Preprocess 7.783 ms
```

야.

처음 PL quant 버전에서 문제가 되었던:

```text
Memcpy ≈ 8.8 ms
```

도 cacheable BO 적용으로:

```text
Memcpy ≈ 0.62 ms
```

까지 해결됐어.

그리고 이미 앞선 검증에서:

```text
RGB order       정상
INT8 quant      exact
crop/resize     within ±1 = 100%
DPU input       [1,640,640,3], fix_point=6
```

까지 확인했으니까, **PL 전처리 설계 자체를 더 의심할 이유는 없어.**

### 다음 최적화 우선순위

지금 남은 시간을 보면:

```text
PL preprocess       7.78 ms   ███████
DPU                17.50 ms   █████████████████
Decode               9.19 ms   █████████
-----------------------------------------
Processing          34.52 ms
```

따라서 HLS를 다시 몇백 µs 줄이는 것보다 먼저 해야 할 게 있어.

**다음 단계는 Camera capture를 별도 thread로 분리하는 것**이 가장 효과적이야.

구조를 이렇게 바꾸는 거야.

```text
Camera Thread
    │
    ├── 계속 최신 frame capture
    │
    └─────────────┐
                  ↓
Processing Thread
          PL preprocess
                ↓
               DPU
                ↓
              Decode
```

그러면 카메라의 약 23 ms와 processing의 약 34.5 ms가 더 이상 단순 합산되지 않아.

이론적으로는:

```text
현재 순차:
23.1 + 34.5 ≈ 57.6 ms
              ↓
약 17 FPS 이하
(+ display 등의 영향으로 실제 13.7 FPS)

병렬 capture:
max(camera 주기, processing)
≈ max(33.3 ms, 34.5 ms)
≈ 34.5 ms

→ 약 29 FPS 근처
```

가 목표가 돼.

물론 실제 OpenCV/V4L2/GUI scheduling 때문에 정확히 29 FPS가 나온다고 보장할 수는 없지만, **현재 13.7 FPS를 크게 끌어올릴 여지가 가장 큰 부분은 capture 병렬화**야.

그리고 그 다음이 `decode = 9.185 ms` 최적화야. DPU 17.5 ms는 현재 B2304 DPU 자체 실행시간이라 소프트웨어 수준에서 쉽게 줄이기 어렵지만, decode는 아직 CPU 작업이라 추가 최적화 여지가 있어.

따라서 지금부터 순서는:

```text
1. ✅ PL crop
2. ✅ PL resize
3. ✅ PL INT8 quant
4. ✅ cacheable BO
5. ✅ PL → DPU 전체 연결
6. ← 지금 여기

7. Camera capture thread화
8. 실제 wall FPS 재측정
9. Decode 9.2 ms 추가 최적화 검토
10. 최종 CPU vs PL 성능 비교/리포트
```

다음은 **현재 `run_camera_pipeline_pl_quant.py`의 기능을 그대로 유지하면서 카메라만 별도 thread로 분리한 버전**을 만드는 게 맞아. 이 단계에서 HLS 코드는 더 이상 수정하지 않아도 돼.
