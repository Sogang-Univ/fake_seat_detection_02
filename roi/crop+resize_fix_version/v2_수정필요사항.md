이제부터는 **HLS 내부의 stage-level pipeline(DATAFLOW)** 단계로 들어가면 돼. 현재 6.57 ms까지 줄인 구조는 내부 loop는 이미 `II=1`이지만, 한 output row 기준으로는 대략 다음처럼 순차 실행되고 있어.

```text
필요한 source row load
        ↓
640 pixel bilinear resize
        ↓
160 × 128-bit output write
        ↓
다음 output row
```

현재 합성 결과에서도 이게 드러났었어.

```text
load_row       ≈ 161 cycles
out_col_loop   ≈ 647 cycles, II=1
write_output   ≈ 161 cycles, II=1

out_row_loop
Iteration Latency ≈ 1292 cycles
Pipelined: no
```

즉 이제 목표는 **각 loop의 II를 더 줄이는 게 아니라 서로 다른 작업을 동시에 돌리는 것**이야.

### 내가 추천하는 순서

처음부터 `load + resize + write`를 전부 DATAFLOW로 뜯지 말고, **1단계에서는 resize와 write만 겹치는 것**부터 하는 게 좋아.

현재는:

```text
resize row 0 ────── 647 cyc
                        write row 0 ─ 161 cyc
                                      resize row 1 ──────
```

이걸:

```text
resize row 0 ──────
           │ stream
           └──────→ write row 0
resize row 1 ──────
           │
           └──────→ write row 1
```

처럼 바꾸는 거야.

핵심은 현재 사용 중인:

```cpp
word_t out_line[DST_SIZE / 4];
```

를 중간 BRAM으로 쓰지 않고,

```cpp
hls::stream<word_t>
```

으로 바꾸는 거야.

---

### 구조 변경 전

지금 대략 이런 형태일 거야.

```cpp
for (int oy = 0; oy < dst_size; oy++) {

    // 필요하면 source row load
    load_row(...);

    // resize
    for (int ox = 0; ox < dst_size; ox++) {
#pragma HLS PIPELINE II=1

        ...
        out_line[...] = ...;
    }

    // DDR write
    for (int w = 0; w < dst_size / 4; w++) {
#pragma HLS PIPELINE II=1

        dst[
            oy * (DST_SIZE / 4) + w
        ] = out_line[w];
    }
}
```

이렇게 하면 resize가 끝나야 write가 시작돼.

---

## 1차 DATAFLOW 구조

다음처럼 두 함수로 분리해.

```text
resize_row()
     │
     │ hls::stream<word_t>
     ▼
write_row()
```

개념적으로:

```cpp
static void resize_row(
    ...,
    hls::stream<word_t>& out_stream
)
{
    ...
}
```

```cpp
static void write_row(
    hls::stream<word_t>& out_stream,
    word_t* dst,
    int oy
)
{
    ...
}
```

그리고 한 row 처리 함수 안에서:

```cpp
#pragma HLS DATAFLOW

resize_row(..., out_stream);
write_row(out_stream, dst, oy);
```

를 사용하는 방식이야.

이렇게 하면 `resize_row()`가 첫 번째 128-bit word를 생성하는 순간 `write_row()`가 바로 DDR로 쓰기 시작할 수 있어.

즉 기존:

```text
647 + 161
≈ 808 cycles
```

에서 이상적으로는:

```text
max(647, 161)
≈ 647 cycles
```

에 가까워질 수 있어.

실제로는 AXI latency와 DATAFLOW overhead가 있으니까 정확히 647 cycle까지 내려온다고 보장할 수는 없어.

---

## 중요한 점: `out_row_loop`에 PIPELINE을 바로 걸면 안 돼

예를 들어:

```cpp
for (int oy = 0; oy < 640; oy++) {
#pragma HLS PIPELINE II=1
```

이렇게 하는 건 우리가 원하는 해결책이 아니야.

왜냐하면 output row 하나가 640 pixel이고, source line buffer를 공유하고 있기 때문에 HLS가 사실상:

> 매 clock마다 새로운 640-pixel row 전체를 시작해라

라는 요구를 받게 돼.

메모리 dependency나 resource 문제 때문에 안 되거나, 엄청난 하드웨어 복제를 요구하게 될 가능성이 높아.

우리가 원하는 건:

```text
pixel-level pipeline    → 이미 II=1 ✅

row 전체를 II=1        → 필요 없음 ❌

stage-level pipeline
resize ↔ write          → 지금 추가할 것 ✅
```

이 차이가 중요해.

---

## 그다음 2차 최적화

`resize → write` DATAFLOW가 성공하면 다음에:

```text
load
 ↕
resize
 ↕
write
```

전체를 겹치는 걸 생각하면 돼.

그때는 **ping-pong line buffer**가 필요해.

예를 들어:

```text
line buffer A
line buffer B
```

외에도 다음 row를 미리 읽기 위한 buffer를 두고,

```text
시간 →

LOAD     row N+1      row N+2
           │
RESIZE   row N        row N+1
           │
WRITE    row N-1      row N
```

형태로 동작시키는 거야.

하지만 이건 현재 bilinear resize에서 `sy0`, `sy1` source row 재사용 관계를 같이 관리해야 해서 첫 번째 DATAFLOW보다 훨씬 복잡해.

특히 우리는:

```text
480 → 640
```

으로 확대하고 있어서 output row가 바뀐다고 항상 새로운 source row를 읽는 게 아니야.

예를 들어 개념적으로:

```text
output y=0 → source row 0,1
output y=1 → source row 0,1
output y=2 → source row 1,2
...
```

처럼 source rows를 반복해서 사용하는 구간이 있어.

따라서 load stage를 무작정:

```text
output row 하나당 source row 두 개 읽기
```

로 만들면 오히려 DDR traffic이 증가해.

그래서 **현재 line reuse 로직은 유지하는 게 중요해.**

# 지금 우리가 실제로 할 작업

순서를 이렇게 잡자.

```text
현재 버전
HLS kernel = 6.57 ms
        │
        ▼
STEP 1
out_line BRAM 제거
        │
        ▼
hls::stream<word_t>
        │
        ▼
resize_row + write_row
DATAFLOW
        │
        ▼
C Synthesis
        │
        ├─ out_col II=1 유지 확인
        ├─ write II=1 유지 확인
        ├─ DATAFLOW report 확인
        └─ 전체 latency 비교
        │
        ▼
xclbin 재빌드
        │
        ▼
KV260 실제 측정
        │
        ▼
STEP 2
load까지 ping-pong DATAFLOW
```

**지금 바로 해야 하는 건 STEP 1이야.**

그리고 이건 기존 코드 일부만 보고 수정하면 실수할 가능성이 있어. 특히 현재 `out_line`에 4픽셀을 어떻게 pack하는지와 `blend4()` 결과의 byte ordering을 그대로 보존해야 해.

그러니 다음 메시지에서 현재 사용 중인 **최적화된 `crop_and_resize.cpp` 전체 코드**를 보내줘. 그러면 내가 그 버전을 기준으로 **동작은 그대로 유지하면서 `resize → write DATAFLOW`만 추가한 전체 코드를 만들어줄게.** 이후 `csynth`에서 정확히 어느 항목을 비교해야 하는지도 같이 보자.
